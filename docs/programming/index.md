# 编程学习概览

围绕科研实验构建可读、可复现、便于排查的代码。

零基础先从一个小任务开始：手里有三条距离记录 `0.5、1.5、0.8` 米，目标是数一数“距离不超过 1 米”的记录有几条。人可以直接数出 2 条；程序只是把判断与计数写成明确步骤。后面再把记录数量增加、把数据改成来自文件或传感器，基本思路仍然相同。

## 写代码之前，先分清这五样东西

| 名字 | 可以怎样理解 | 本站例子 |
| --- | --- | --- |
| 源代码 | 人写给计算机的步骤文本 | Python 的 `.py` 文件、C++ 的 `.cpp` 文件 |
| 编辑器 | 修改这些文本的工具 | 输入、保存代码的窗口 |
| 终端 | 向开发工具发指令的窗口 | 输入编译或运行命令的位置 |
| 编译器 / 解释器 | 按语言规则处理代码的工具 | C++ 编译器、Python 解释器 |
| 程序输出 | 代码执行后的文字或数据 | `达标记录：2/3` |

**代码、命令、输出是三种不同内容。** `print(...)` 写在 Python 代码里；`cmake --build build` 输入终端；显示出的“达标记录”只是结果，不需要再贴回代码。阅读每个代码框前，先看框的语言与上方说明。

本站的强化学习示例以阅读为主：把注释、公式和数据流对照起来即可。C++ 教程另外提供可自行实践的编译步骤。无需为了阅读就先安装所有工具。

## 把需求拆成四步，再写程序

沿用三条距离记录，先写出程序的输入与预期答案：

1. **输入**：`[0.5, 1.5, 0.8]`，每项单位是米；阈值是 1.0 米。
2. **处理**：从第一条开始，检查是否小于或等于阈值，符合就把计数加一。
3. **输出**：达标数量 2，总数 3，比例约 66.7%。
4. **边界**：等于 1.0 算不算达标？本例算。没有记录怎么办？不能把 0/0 当成比例，应明确显示“无数据”。

这四步叫作把需求说清楚，不需要先懂复杂语法。若程序输出与手算不同，先用这一小组数据定位哪一步出错。完整的带注释示例与逐步追踪见 [Python 阅读入门](python-reading.md)。

### “没有报错”与“答案正确”是两回事

假设真实距离为 80 厘米，程序却把数值 80 当成米，与 1 米比较。语法完全可以正确，但会把本应达标的记录判为不达标。把字段叫作 `distance_m`，并在接收数据时把厘米除以 100，可让数据含义更清楚。

检查程序时至少准备：一条明显达标的记录、一条明显不达标的记录、恰好在边界的记录、缺失数据。每一条都有事先想好的答案，才能区分程序是否符合需求。

## 一次实验应留下什么

1. **配置**：参数集中管理，记录随机种子。
2. **环境**：保存依赖版本与运行方式。
3. **日志**：区分训练指标、运行事件和错误信息。
4. **结果**：输出图表、评估数据和失败案例。
5. **说明**：写清如何复现以及当前已知限制。

## 代码整理原则

### 一个容易复现的记录，比一句“效果不错”更有用

假设某次实验输出 `distance = 2.5`。别人还不知道这是米还是像素、来自哪一帧、用了哪组参数。记录成“时间戳、坐标系、距离单位、参数版本、结果”后，才能判断它是否可与另一次实验比较。

学习代码也按这个顺序读：**输入是什么 → 如何处理 → 输出代表什么 → 哪里可能失败**。遇到长程序先圈出这四部分，不必从第一行开始逐字背。

优先让一个最小实验完整运行，再抽取复用模块。观测与动作接口要明确数据形状、坐标系和单位；训练与评估使用独立入口，避免把训练表现当作评估结果。
