# 13 · 并发与线程

**示例标准：C++20**

并发让多项工作在时间上交错推进。线程可能并行执行，但线程越多不一定越快；共享数据如果没有协调，还可能得到错误结果。


!!! tip "读完这页，你应该能做到"

    检查共享数据如何同步，读取最终结果前如何等待。

    **先会这些就够了**：Lambda、生命周期。

**生命周期**：jthread 持有任务，等待完成再读最终结果；**共享数据**：atomic 计数，多个字段可用锁保护；**停止与性能**：停止请求需要合作，线程更多不一定更快。


## 两个人同时记数，为什么会漏掉一次

普通的“加一”可以理解为读取旧值、计算新值、写回。如果两个线程都先读到 0，各自算出 1，再各自写回 1，总共做了两次工作，计数却只增加一次。在 C++ 中没有同步的这种冲突访问还构成数据竞争，不能把这张示意表当作唯一可能结果。

atomic 的 fetch_add 把这次读、改、写组成一个原子操作：其他线程不能插进这个计数操作中间。它保护计数，却不表示全部工作已经结束，所以最后还要等线程完成。

| 要保证的事情 | 本例用什么实现 |
| --- | --- |
| 计数更新不发生数据竞争 | atomic 的 fetch_add |
| 读最终结果时两份工作都做完 | 内部作用域结束，jthread 等待 |
| 工作期间计数器始终存在 | samples 创建在外层作用域 |

每个线程做 1000 次，总共 2000 次。哪个先完成并不重要，计数同步与等待条件才重要。并发不等于加速：任务太小，创建线程和协调的成本可能比计算更高。


## 先保证生命周期，再保护共享数据

`std::jthread` 在析构时请求停止并等待线程结束，减少忘记 `join` 的风险。但停止请求是合作式的：工作函数必须主动检查停止标记，不能强制打断任意阻塞操作。

`mutex` 像同一份资料的一把锁，`lock_guard` 用 RAII 在作用域内持锁。`atomic` 适合独立计数等原子操作；多个字段一起维持不变量时，一个原子计数器并不能替代整体同步设计。

两个线程没有同步地读写同一普通变量，且至少一个写，可能构成数据竞争，这是未定义行为。不要凭“只加一下”判断它安全。

## 一条主线程，怎么变成三条执行路线

程序进入 main 时已有一条主线程。创建 first 启动一条工作线程，创建 second 再启动一条；工作线程执行 collect，主线程继续往下走。它们的先后顺序不是按屏幕上“先写 first、再写 second”就能完整决定的。

```text
主线程：创建 samples → 启动 first → 启动 second → 等待两者 → 输出总数
first：                 collect：累计 1000 次 ─────完成
second：                              collect：累计 1000 次 ──完成
```

图中的宽度只是示意，不是耗时测量。两份 collect 可能交错，也可能在不同 CPU 核心并行；不能根据图推断哪一份一定先结束。

## 程序里每个新动作都有一项责任

| 写法 | 它保证什么 | 它没有保证什么 |
| --- | --- | --- |
| `std::atomic<int> samples{0}` | 这个对象支持原子访问操作 | 不让其他任意变量自动线程安全 |
| `samples.fetch_add(1)` | 一次加一作为不可分割的更新完成 | 不表示整个工作函数已结束 |
| `[&samples]` | 两条工作路线访问同一个计数器 | 不自动延长计数器生命周期 |
| `std::jthread first{collect}` | 启动执行 collect 的线程并管理它 | 不保证立刻跑完，也不保证提速 |
| 内层 `}` | 销毁仍可连接的 jthread，请求停止并等待 | 不会强制中断工作函数 |
| `samples.load()` | 以原子读取取得当前值 | 若没等工作结束，只能说是当时的值 |

jthread 的等待行为来自 [标准草案中的析构约定](https://eel.is/c++draft/thread.jthread.class)：当它仍可连接时先请求停止，再 join。停止请求需要工作函数配合；本例没有接收停止令牌，两个有限循环都会正常跑完。

## 为什么不能把加一拆成“读取再写入”

即使 samples 是 atomic，先 load，再根据旧值 store，也不等于 fetch_add：两条线程可能各自读到相同旧值，再写回相同新值，造成逻辑上的丢失更新。要做“给同一个总数加一”，这里选的是一次完整的原子读改写操作。

普通 int 的无同步冲突访问更严重：在 C++ 规则下可能构成数据竞争，程序行为没有定义。不能以“我试了几次刚好是 2000”证明安全，也不应把某个编译器上的偶然结果写成必然输出。

当任务涉及一组字段，例如同时修改位置和时间戳，单独的原子计数不能保持整组数据一致。那时通常需要把整段相关操作放在同一把 mutex 保护下；lock_guard 帮助把加锁与解锁绑定到作用域。初学先理解本例一个计数器，再扩展到更大的共享状态。

若只是两次小循环顺序累加，完全可以不用线程。这里的目标是看懂生命周期、共享访问和等待三件事，实际项目是否值得并发还应测量耗时与协调成本。

## 完整示例

```cpp
#include <atomic>
#include <iostream>
#include <thread>

// 程序入口；下面按顺序执行示例步骤。
int main() {
    // 共享计数器，用原子操作避免竞争导致的丢失更新。
    std::atomic<int> samples{0};
    {
        // 引用捕获计数器；计数器必须比工作线程活得久。
        const auto collect = [&samples] {
            for (int i = 0; i < 1000; ++i) {
                // 原子的读—改—写，默认使用顺序一致的内存序。
                samples.fetch_add(1);
            }
        };
        // 启动工作；对象析构会请求停止并等待线程结束。
        std::jthread first{collect};
        // 再启动一份相同工作，两份工作借用同一个 samples。
        std::jthread second{collect};
    } // 先等待 second，再等待 first；两份工作都结束后才往下走。
    // 内部作用域已结束，两个线程完成后读取最终计数。
    std::cout << "samples: " << samples.load() << '\n';
}
```

```powershell

./concurrency.exe
```

预期输出：

```text
samples: 2000
```

## 怎样读这段代码

两个线程各增加 1000 次。`fetch_add` 是原子的读—改—写，所以不会丢掉某次增加。我们保留默认内存顺序，初学不急着换成 relaxed。

内部作用域结束时，先销毁第二个线程对象，再销毁第一个，二者都会等待各自任务完成。计数器在外部作用域，仍然存在，所以引用捕获有效。最终读取发生在线程全部结束之后，结果稳定为 2000。

本例工作函数不接收停止令牌，也不会响应停止请求，但任务是有限循环，可以正常结束。它不是实时采集系统。

## 常见错误

- 把 atomic 换成普通 int，即使偶尔输出 2000，也不能证明程序正确。
- `volatile` 不提供线程同步，不能代替 atomic 或 mutex。
- jthread 等待不代表一定很快退出；工作线程一直阻塞时析构也可能一直等待。
